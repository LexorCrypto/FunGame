## Findings (verbatim)

FAIL — 3 should-fix defects.

- [P2] `src/main.js:102` — Scoring ignores per-enemy and endless-cycle multipliers. Roach Queen brood awards 100 instead of its specified 50, while cycle `c ≥ 2` enemies never receive the required `×c`.
- [P2] `src/main.js:134` — Shield pickup is now reachable, but continuous enemy/boss/hazard overlap consumes the shield and then kills the player on the next frame. It needs brief separation/invulnerability after absorption.

## Disposition

- **[P2] Roach Queen brood over-scored (100 vs 50) → DEFER (real minor scoring inaccuracy).** Verified: `main.js:102`'s new `this.scoring.addEnemyKill(enemy, diving)` wiring passes `diving = enemy.diveState === 'diving'`, and `BossRoachQueen.updateBrood` always puts spawned `cockroach` entities into the diving pattern immediately after spawn (§7.4: "отродья Королевы пикируют тем же паттерном сразу после спавна"). `Scoring.js`'s generic `enemyKillPoints` then applies the formation "diving ×2" rule (§9) unconditionally, doubling the boss-specific flat 50 (§7.4) to 100. `ENEMY_POINTS.cockroach` itself is correctly 50 — the bug is the interaction between the generic diving-multiplier rule and a boss brood that is *always* diving by design. This scoring/wiring path (`main.js:102`, `diving` detection) is new in this commit, so it is a genuine defect introduced here, not pre-existing. Cosmetic/scoring-only (no crash, no soft-lock); deferred to a follow-up scoring-correction ticket rather than fixed here (read-only audit).
- **[P2] Missing endless-cycle `×c` score multiplier → DEFER (pre-existing gap, first exposed here).** Confirmed: `Scoring.js` (`enemyKillPoints`, `addEnemyKill`, `addBoss`) has no `cycle` parameter anywhere; `WaveDirector.js` tracks `cycle` for wave/enemy modifiers (sway/dive/bullet speed per §14) but never threads it into scoring. This gap originates in the scoring system itself, added in an earlier commit (`a882ba5`, FUN-17), *before* the three audited commits — `61ec271` is only the first commit that wires `addEnemyKill` into live gameplay, making the pre-existing gap reachable for the first time. Endless-cycle (wave 26+) is late-game and does not affect the M1–M6 acceptance path; deferred to the FUN-17/scoring follow-up.
- **[P2] Shield-absorb "no i-frames" → ACCEPTED as by-design (already resolved, not a defect).** Verified `src/entities/Player.js:119-132` at HEAD: `hit()` already calls `this.grantInvulnerability(1000)` immediately on shield absorb, exactly matching the documented decision "Shield grants 1.0 s i-frames on absorb (§8 doesn't specify) — else continuous contact eats a life next frame." `git blame` confirms this line was added by `b312634` ("FUN-16 followup: shield grants brief i-frames on absorb"), which predates `61ec271` and is untouched by its diff (`Player.js` is not in `61ec271`'s changed-file list). Codex, scoped to auditing only `61ec271`'s diff, didn't see this pre-existing cross-file fix in `Player.js`. Not a real defect.
- **[P2] Death-pause doesn't freeze the whole world → DEFER (interpretation ambiguity, documented in code).** Confirmed at `main.js:240-256`: only `formation`, `diveDirector`, `waveDirector` (which also gates `boss.update`) and player firing are skipped while `this.player.dead`; Arcade physics integration, existing projectile motion, hazard timers, and tweens are not explicitly paused. SPEC §14's transition table distinguishes the two rows: "Смерть игрока | 1.5 s пауза | взрыв, затем респаун" (no "world frozen" language) vs. "Пауза | Esc | оверлей «ПАУЗА», **игровой мир заморожен**" (explicit full freeze) — only the Esc-pause row states a full world-freeze contract. The existing code comment ("SPEC §14: смерть игрока — 1.5 s пауза: строй/дайв/волны заморожены, пока корабль мёртв") documents this narrower interpretation deliberately. Practically inert: `player.body.enable = false` during the death window, so the player cannot be re-hit by anything still moving. Treated the same as the other pending-owner-ruling SPEC ambiguities already on record (BigMacaque landing circle, shield i-frame duration); not fixed here (read-only audit).
